# Architecture decisions and release readiness — external research

**Date:** 2026-08-24
**Purpose:** Decide whether an Accepted ADR with undischarged obligations is a fact a release should measure.
**Scope:** ADR practice and templates, decision-confirmation prior art, architecture testing, deployment readiness gates.
**Issue:** [#141](https://github.com/tosin2013/repo-governor/issues/141) · **Consumed by:** ADR-032.

A release here measures the tag, the version strings, conformance, and the artifact's
shape. It measures nothing about architecture. Meanwhile an ADR can be `Accepted`, its
obligations never built, and every check in this repository stays green.

This document establishes what is true outside the repository before deciding anything
inside it — the same role as
[`2026-08-17-external-landscape.md`](2026-08-17-external-landscape.md), which ADR-001 was
built on.

---

## Finding 1 — The prior art exists, is optional, and nobody here uses it

MADR — the most widely adopted Markdown ADR template — carries an optional
**`Confirmation`** section whose stated purpose is to record *how the implementation of,
or compliance with, the ADR is evaluated*. Its own primer is blunt about why it exists:

> The purpose of this optional section is to remind everybody who is involved that it is
> not enough to decide; design and implementation actions are required to bring the AD to
> life.

Suggested means of confirmation are a design or code review, or a test — the primer names
ArchUnit specifically. The framing worth stealing is that a Confirmation section *"turns
the ADR into a testable claim about the system rather than an essay."*

**Relevance to Repo Governor.** This is precisely the missing field. Our ADRs state what
follows from a decision and never state how anyone would know it happened. The concept is
not novel and does not need inventing; it needs adopting.

**Constraint it imposes.** It is **optional** in MADR, and optional fields in templates
are the ones that go unfilled. Any adoption here that leaves it optional will reproduce
exactly the current situation with a new heading.

**Non-adoption argument, partial.** MADR's Confirmation is satisfied by *"a design or code
review"* — a human act with no artefact. That is a legitimate confirmation in MADR's
world and is not machine-readable, so importing the field wholesale imports a category
this project cannot check. See Finding 2 for where the line actually falls.

Sources:
- [ADR Template | MADR](https://adr.github.io/madr/decisions/adr-template.html)
- [The Markdown ADR (MADR) Template Explained and Distilled](https://ozimmer.ch/practices/2022/11/22/MADRTemplatePrimer.html)
- [ADR Templates | Architectural Decision Records](https://adr.github.io/adr-templates/)

## Finding 2 — Architecture tests enforce form, never substance

ArchUnit is the canonical tool for making an architectural decision mechanically
checkable, and its limits are documented and sharp. It verifies dependency direction,
layering, package cycles, naming — structural facts recoverable from bytecode. It
explicitly cannot verify that services interact correctly, that infrastructure is deployed
correctly, or anything outside its own language boundary. The clearest statement of the
boundary: these tests *do not check substance, their purpose being to enforce form.*

It also has a subtler failure mode worth recording, because this project has the same one:
ArchUnit reads generated bytecode, so a dependency present in source can vanish before the
check sees it — an inlined constant defeats a layering rule that looks correct.

**Relevance to Repo Governor.** This bounds any mechanism before it is designed. Sorting
this repository's own obligations against that line:

| kind | example | confirmable? |
|---|---|---|
| **structural** | ADR-011: the engine imports nothing outside a stdlib allowlist | yes — `conformance/imports.py` does it, by AST |
| **procedural** | ADR-011: typing *checked in CI* | yes, but by a different means: does a pipeline step exist |
| **substantive** | ADR-008 §5: *publish the portability number in the README as a standing claim* | only partly — that a number is present is checkable; that it is **true** is a measurement |

Three obligations, three different kinds of check. A mechanism that assumes one kind will
silently fail on the other two.

**Constraint it imposes.** `conformance/imports.py` already refuses to grep source text for
exactly ArchUnit's reason — a string in a comment is not an import — and it took two
shipped defects here to learn that. Any future check inherits this: it must read structure,
not prose about structure.

**Non-adoption argument.** ArchUnit itself is Java and irrelevant as a tool. What
transfers is the taxonomy and the honesty about the boundary, not the library.

Sources:
- [Why test your architecture? — ArchUnit](https://www.archunit.org/motivation)
- [ArchUnit User Guide](https://www.archunit.org/userguide/html/000_Index.html)
- [Enforcing Architecture with ArchUnit in Java](https://mydeveloperplanet.com/2025/04/30/enforcing-architecture-with-archunit-in-java/)

## Finding 3 — Immutability decides where discharge state may live

ADR practice is consistent across every source consulted: an Accepted ADR is
**immutable**. Content changes beyond typos and broken links are forbidden; anything that
changes meaning goes in a new ADR that supersedes the original, with links in both
directions. Status is the one field that moves, and it moves only to `Superseded`.

**Relevance to Repo Governor.** This forecloses the most obvious design. Discharge state
**cannot be recorded in the ADR body** — not as a checkbox, not as a status word, not as a
struck-through line. An ADR that says "Accepted, consequence 4 outstanding" has edited a
decision to describe the world, which is the thing immutability exists to prevent.

Whatever records discharge must live elsewhere and join on the ADR id. That is the same
shape as `.repo-governor/acceptance/<id>.json`, which is keyed by authority id and sits
outside the tracker it refers to.

**Constraint it imposes.** It also explains the one hand-rolled marker this repository
already has. ADR-011's implementation plan item 1 is struck through and marked **done** —
an edit to an Accepted ADR. It is the only one of 99 plan items so marked, and by the
immutability rule it should not have been done at all.

Sources:
- [Maintain an architecture decision record — Microsoft Azure Well-Architected Framework](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record)
- [Architectural Decision Records — lecture notes, UQ CSSE6400](https://csse6400.uqcloud.net/handouts/adr.pdf)
- [Architecture Decision Records (ADRs) — IcePanel](https://icepanel.medium.com/architecture-decision-records-adrs-5c66888d8723)

## Finding 4 — Readiness gates exist and do not consult architecture

Deployment readiness gates are an established pattern: aggregate the fragmented evidence
of a release — CI status, security scans, artifact signing, rollback plans, test coverage —
into one auditable decision, so that shipping is a recorded judgement rather than a vibe.

Nothing found joins that pattern to architecture decisions. Readiness gates consult the
build; ADR tooling consults the ledger; the two do not meet.

**Relevance to Repo Governor.** The gap is real rather than a gap in the searching. But a
gap is not automatically an opportunity — see the rollup.

**Non-adoption argument.** The readiness-gate pattern is a **gate**, and this project has
already refused that surface. Issue #46's enforcement stays deferred because a pull request
does not carry an authority id and ADR-018 forbids assuming one. Importing the pattern
would import the blocking behaviour it is named for.

Sources:
- [Deployment Readiness Gate: Turning Fragmented Release Evidence into an Auditable Decision](https://daily.dev/posts/deployment-readiness-gate-turning-fragmented-release-evidence-into-an-auditable-decision-zigz3hww7)
- [8 best practices for creating architecture decision records | TechTarget](https://www.techtarget.com/searchapparchitecture/tip/4-best-practices-for-creating-architecture-decision-records)

## Finding 5 — Measured on this repository's own ledger

Run against `docs/adrs/` on 2026-08-24, not asserted:

| | |
|---|---|
| ADRs on disk | 29 |
| Accepted | 23 |
| Accepted ADRs with a `## Consequences` section | **23 of 23** |
| ADRs with anything `Confirmation`-shaped | **0** |
| consequence items across the 23 | **168** |
| Accepted ADRs with an `## Implementation Plan` | 18 |
| plan items across those | **99** |
| plan items carrying any discharge marker | **1** |

Every Accepted decision states what follows from it. None states how anyone would know
that happened. **267 post-acceptance obligations, one discharge marker.**

`## Acceptance conditions` exists on exactly three ADRs — 024, 030, 031 — all `Proposed`.
Those are gates *to* acceptance and are tracked in prose by hand; none survives acceptance.

**The worked example.** ADR-011 carries obligations in three different sections, and they
have three different fates:

- `## Decision` item 6, *no network access in the engine* — enforced by
  `conformance/imports.py`
- `## Implementation Plan` item 4, *a CI check for the stdlib allowlist* — the same suite,
  enforced
- `## Decision` item 5, *static typing via annotations checked in CI* — **never enforced,
  and the engine carries no annotations for a checker to read**

One Accepted ADR, three obligations, two mechanically enforced and one invisible, with
nothing in the repository able to tell them apart. The two that were discharged were
discharged because a person remembered — a mechanism that works until it does not, and
that leaves no evidence either way.

## What changes

1. The concept is **not novel**; MADR already has the field, and adopting it costs a
   heading rather than a design. → **ADR-032**
2. Mechanical confirmation is bounded to **structural** obligations, with procedural ones
   checkable by a different means and substantive ones not checkable at all. Any mechanism
   must say which kind it handles. → **ADR-032**
3. Immutability means discharge state **cannot live in the ADR**. → **ADR-032**
4. The readiness-gate pattern must not be imported, because this project has already
   refused gating on a signal ADR-018 forbids assuming. → **ADR-032**, and it keeps
   [#46](https://github.com/tosin2013/repo-governor/issues/46) deferred
5. The measured baseline — 267 obligations, one marker — is the evidence the decision rests
   on, and the number to re-measure if anything is built. → **ADR-032**

## What this does not settle

- **Whether the gap matters enough to close.** Two of ADR-011's three obligations were
  discharged without any mechanism. A sample of one ADR cannot say whether remembering
  usually works, and *"nothing tracks this"* is not the same finding as *"this goes
  wrong"*. §54's failure conditions warn against blocking routine reversible work
  excessively, and a mechanism that fires on 267 items would do exactly that.
- **Whether this repository's ledger generalises.** Its ADRs were written by one author in
  one dialect against one project's conventions — the limitation
  `docs/adrs/README.md:121` already records about its adapters, where the stated bar is
  *"a third-party adapter is the real test."* `adapters/adr` reads only 92% of statuses
  across 439 real ADRs; nothing here suggests obligations are stated more consistently than
  statuses are. The equivalent measurement on repositories this project does not own is
  [#39](https://github.com/tosin2013/repo-governor/issues/39)'s precedent and has not been
  done.
- **What a "release scope" even is for this purpose.** An ADR is not admitted to a
  milestone. Joining decisions to a release would need a relation that does not exist in
  the domain model, and inventing one is a larger act than it appears.
- **Whether a substantive obligation can be confirmed at all.** ADR-008 §5's *"publish the
  portability number as a standing claim"* is checkable for presence and not for truth.
  Half a check may be worse than none, because presence reads as discharge.
